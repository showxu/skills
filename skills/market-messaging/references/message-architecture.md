# Message Architecture

Use this reference when the task needs positioning, a value proposition, or a
message system before drafting channel copy.

## Inputs

- Audience: who the message is for, their role, skill level, and urgency.
- Job: what the user is trying to accomplish, avoid, learn, decide, or fix.
- Problem: the current pain, cost, limitation, or friction.
- Promise: the useful change the product can credibly make.
- Differentiator: why this product is meaningfully different for this user.
- Proof: shipped features, visible UI, metrics, reviews, quotes, awards,
  integrations, certifications, or demos.
- Objections: switching cost, trust, price, complexity, privacy, migration,
  platform support, or missing proof.

## Message Map

```text
Audience:
Job:
Problem:
Primary promise:
Proof:
Differentiator:
Objection to answer:
Primary CTA:
Words to use:
Words to avoid:
```

## Operating Rules

- Keep strategy as input. The deliverable should be copy, message hierarchy,
  or review notes that can be used in a public surface.
- State the audience in plain language before writing. Copy that targets
  everyone usually targets no one well.
- Convert features into benefits only when the causal path is clear:
  feature -> user action -> user outcome.
- If the proof is weak, soften the promise instead of adding hype.
- Treat a differentiator as useful only when it changes the user's decision.
- Keep one central message and two or three support points. More is usually a
  page architecture problem, not a stronger message.

## Compact Examples

Feature-only:

```text
Syncs documents across devices.
```

Benefit with proof shape:

```text
Pick up the same draft on iPhone, iPad, or Mac without emailing files to
yourself.
```

Unsupported superlative:

```text
The fastest way to manage projects.
```

Safer rewrite:

```text
Plan tasks, files, and deadlines from one project view.
```
