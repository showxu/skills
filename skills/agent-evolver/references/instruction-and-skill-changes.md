# Instruction and Skill Changes

## Multi-source practices

Treat supplied OpenAI, Anthropic/Claude, Apple, Swift, and other primary guidance
as evidence to inspect, not automatic replacement authority for local policy.
Record the source URL or supplied excerpt, publisher, version/date, the concrete
recommendation, its model/host/platform conditions, and the local artifact it
could improve. Mark supplied excerpts as excerpt evidence when the current
page or full context has not been verified.

Separate source facts, situational recommendations, and accepted local
invariants. When vendors recommend different techniques, first test whether
their hosts, models, task sizes, or tool capabilities differ. Keep the useful
conditions instead of blending them into a universal instruction. If a new
recommendation would alter a valid local principle, show the exact proposed
semantic change and evidence for the owner to decide.

For example, a context-loading recommendation for one agent host does not
establish another host's instruction discovery behavior. Inspect actual
rendered input or a bounded host probe before claiming loss or truncation.
A newer model's prompting advice does not remove existing provenance,
permission, or acceptance obligations.

## AGENTS.md

AGENTS.md owns agent guidance; repository architecture docs retain their own
authority. Inspect global, repository, and relevant nested instruction
boundaries using the actual host's discovery behavior.

Repair verified stale paths, command facts, and navigation at the owning
source. Preserve effective First-Principles, Canonical Artifacts, Authority,
Boundary Guardrails, and other project principles verbatim. Keep independent
repositories independently usable. A directory list and a rule resolving a
real ownership conflict have different purposes.

For shared templates or generated projections, identify the authoritative
source and supported synchronization mechanism first. Propagate only
source-owned shared content and preserve local differences. Similar wording
alone is not proof that two files share a source.

Meaningful changes to policy, authority, permission, validation standards, or
ownership require an explicit owner decision. Prepare a concrete diff and
impact first; continue unrelated authorized repairs. Do not create blanket
negative rules from a rejected idea.

## Skills

Read the target entry, declared maintenance architecture, and implicated
references/rules/scripts/templates before a substantive edit. Preserve
engineering choices, counterexamples, failure modes, validation routes,
source receipts, and still-needed compatibility. Keep domain rules in their
existing owner; do not compress every skill into an API index or thin router.

For maintained source merges, follow the target's source-role map and patch
policy. In skill-creator, preserve both Anthropic's co-development, eval,
comparison, review, feedback, and packaging semantics and OpenAI's anatomy,
trigger, progressive reading, metadata, and scaffolding semantics. Raw
receipts stay raw; authoring and local composition follow their owned layers.

Prefer a focused reference update when the trigger and responsibility remain
correct. Revise descriptions and metadata together when the actual task
boundary changes. New skill placement, splits, renames, and retirement need
their own accepted architecture decision and capability transfer.

Source-only audits return packets. For an authorized implementation request,
hand those packets to the established authoring workflow and complete the
required per-skill checks. Do not stop at a proposal merely because the
source-verification phase is read-only.

## Platform and version evidence

For Swift/Apple and similar versioned domains, distinguish compiler, language
mode, SDK declarations, deployment targets, compiled examples, and real
runtime evidence. Keep appropriate old-system branches and project targets.
A compiled declaration is not proof of UI lifecycle, performance, device,
permission, cloud transmission, or real model behavior.

Only preserve permission, output validation, compatibility, or other guards
that belong to the relevant official contract or concrete engineering
practice. Do not attach the same generic restrictions to every skill.

## Overlap and replacement

Compare precise source/installed identities, actual responsibilities,
independent assets, and relevant host conditions. Similar names do not prove
redundancy; different vendor wording does not by itself prove conflict.

After either participant or its source changes, recheck affected overlap and
replacement decisions. Before an authorized retirement, verify retained
capabilities with the receiver and actual discovery/usage conditions, then
update active references and installation through their owners. Preserve
correct historical provenance. An unverified candidate remains a candidate.
