# GitHub Markdown Preview

Use this route when the test target is Markdown that GitHub renders: a
repository README, a profile README, or other Markdown viewed on github.com.
GitHub's renderer produces the HTML under test, so treat the result as a static
HTML target and run the normal QA workflow on it.

## Why Render Through GitHub

- GitHub's sanitizer decides which HTML survives. For example, `<picture>`,
  `align`, and `width` survive, while `style`, scripts, and most classes do not.
  A local Markdown renderer cannot prove what GitHub will publish.
- `gh api markdown` with `mode: gfm` and a repository `context` returns that
  sanitized HTML.
- Remote images come back rewritten to camo proxy URLs, wrapped in links to the
  same proxy. The original URL survives only in `data-canonical-src`.

## Build The Preview

```bash
python3 skills/webapp-testing/scripts/render_github_markdown.py <markdown-file> \
  --context <owner>/<repo> \
  --out <preview-dir> \
  --width <article-px> \
  --map '<published-url-prefix>=./<local-dir>/'
```

- The script unwraps camo URLs, applies `--map` replacements, and writes
  `<preview-dir>/index.html` styled with `github-markdown-css`. That stylesheet
  follows `prefers-color-scheme`.
- Copy relative assets into `<preview-dir>` at the same relative paths.
- Use `--map` for images that exist only after publishing: files generated by
  CI, files on another branch, or files not pushed yet. Put local copies at the
  mapped path.
- The script lists remote images still loaded from the network. Those prove
  nothing about unpublished content.
- Set `--width` to the width of `article.markdown-body` measured on the target
  github.com page. GitHub's article has no padding, so this is the content
  width; the preview adds its padding outside it. At a 1280 px window, profile
  READMEs measured 846 px and repository READMEs 838 px. Re-measure when the
  layout looks different.
- Point images that count requests, such as profile-view counters, at a
  throwaway id. Every preview load increments the real counter otherwise.

Serve the directory with a local static server bound to `127.0.0.1`. Confirm
the port answers before navigating, and stop the server when QA ends.

## Capture Evidence

Check each scheme and viewport the readme supports: light, dark, and a narrow
mobile width such as 390 px.

GitHub's phone column is narrower than the preview's at the same viewport,
because the preview pads 15 px on each side under 768 px. On a 390 px phone,
profile READMEs measured 308 px and repository READMEs 324 px. For a faithful
mobile check, set the emulated viewport to the measured column plus 30 px.

- Set the viewport and `prefers-color-scheme` emulation, then wait for remote
  images to finish loading.
- Count broken images: an image is loaded when `complete && naturalWidth > 0`.
- Confirm each `<picture>` `currentSrc` matches the active scheme.
- On mobile, confirm `document.documentElement.scrollWidth` does not exceed
  `innerWidth`.
- Check the text contrast of custom images in both schemes, such as SVG banners
  and stat cards.
- For a row of inline badges, compare the row's total width with the target
  column. A row that is slightly too wide strands one badge on a second line.
- For an image inline with text, such as a badge beside a link, compare the
  image's vertical center with the text's. Images sit on the baseline by
  default, which lifts a 20 px badge about 4 px above 16 px text. GitHub keeps
  `align` on images: `align="absmiddle"` maps to `vertical-align: middle` in
  every engine, while Chromium treats `align="middle"` differently.
- Screenshot each state and review it. DOM checks alone do not prove a visual
  claim.

Capture discipline for CDP-driven backends:

- Run captures one at a time per tab. Overlapping emulation changes or
  screenshots in one tab produce images of the wrong state.
- A new tab drops emulation. Re-apply the viewport and color scheme before
  capturing.
- For a full-page clip, first set the viewport height to the document height.
  Capturing beyond the viewport can duplicate content.
- On live github.com pages, scroll the target into view and clip inside the
  viewport. Capturing beyond the viewport there repeats the top of the page.
- Clear emulation when finished.

## Verify After Publishing

- When signed in, github.com picks `<picture>` sources from the account's theme
  setting, not the OS. Emulating `prefers-color-scheme` does not switch them.
  Check `currentSrc`, or use a signed-out session. Do not change the account
  theme to test.
- `raw.githubusercontent.com` caches responses for about five minutes,
  including 404s returned before a file existed. Query strings do not bypass
  this cache. Before reporting a broken image, confirm the file exists with
  `gh api 'repos/<owner>/<repo>/contents/<path>?ref=<branch>'`, then recheck
  once the cache expires.
- Third-party images load through camo, which gives up on slow upstreams. A
  single failed load right after publishing can be transient: fetch the camo
  URL with curl and reload once before reporting it broken.
- When a workflow generates images, verify in this order:
  1. The run's conclusion.
  2. File contents on the target branch. Presence alone is not enough; an error
     card can sit where the real image should be.
  3. The rendered page.

## Report Additions

Add these to the QA report:

- Renderer and context.
- Mapped URLs.
- Schemes and viewports captured.
- Broken-image count.
- Surfaces still unverified, such as GitHub mobile apps, other operating
  systems' fonts, or remote images that were not mapped.
